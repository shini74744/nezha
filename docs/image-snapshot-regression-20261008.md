## 第 4 项复测结论

原失败发生在每轮 118 个节点并发、每节点连续写 5 个样本的隔离 SQLite 测试；报错是单次写入的 `context deadline exceeded`。整轮耗时与单次写入的 5 秒期限不是同一个指标。

- 原提交 `ae537db` 重跑，以及 `5b49594`、`db639b1` 各 10 轮 Windows 测试均未再次超时；早期通过不能排除偶发问题。Linux 原实现连续 10 轮通过，每轮约 1.49–1.64 秒；Windows 早期每轮约 9.73–11.58 秒。
- 发布前，提交 `253c3bc` 的 [Windows 复测](https://github.com/shini74744/nezha/actions/runs/37743584890) **再次失败**：节点 94 的第 0 个样本 `context deadline exceeded`，该轮总时长 15.21 秒。随即暂停发布，生产仍运行旧版。
- 原实现每条上报分别提交一次 SQLite 事务，5 秒期限包含排队时间。118 个节点突发上报产生大量串行磁盘提交，正常排队已接近期限；存储/调度抖动可使队尾超时。不能从 CI 日志断言某种硬件或杀毒软件是唯一诱因。
- 修复提交 `486d24c3e2c3c73d662bad4760f3022bcbe29739` 将同一数据库已排队的上报合并为最多 128 条的小批次提交，不等待凑批，不改变原 5 秒期限；每条调用仍等事务提交或回滚后才返回，因此不会提前释放停机排空或节点身份保护。
- 单条报告使用保存点隔离，快照与该报告的流量计数同时成功或回滚；整批提交失败时所有报告均返回失败。保留过期拒绝、旧身份拒绝、每秒合并及一分钟保留规则。无任务时写入 worker 自动退出。
- 新增固定 50ms 提交延迟的 118 节点/590 样本回归、单条失败隔离、整批回滚、过期队列、提交前不得返回、乱序/重复流量不重计等用例。定向 race 连续 5 次通过；Windows CI 增加普通与慢提交两种场景各连续 10 次。最终 CI 与完整回归结果另列，不以早期通过覆盖失败记录。

节点快照指最近一分钟的节点状态持久化，不是 BGP 历史快照。Windows 后端测试结果不等于 Windows 浏览器或 Windows Agent 有同样问题。
