# 统一仓库：主面板与 Agent

从主面板 **v0.0.3**、Agent **v1.0.1** 起，源码、文档、安装脚本和二进制统一维护于 [shini74744/nezha](https://github.com/shini74744/nezha)。

旧 [shini74744/agent](https://github.com/shini74744/agent) 仓库保留源码历史和原发行版，不删除、不继续发布，也不作为新版本的备用下载源。新程序遇到下载失败会明确失败，不回退旧仓库或上游。

## 两个程序、独立版本

| 项目 | 主面板 | Agent |
| --- | --- | --- |
| 合仓首版 | v0.0.3 | v1.0.1 |
| 当前正式版本 | v0.0.6 | v1.0.3 |
| 当前 Git Release 标签 | `v0.0.6` | `agent-v1.0.3` |
| 当前程序版本 | `v0.0.6` | `1.0.3` |
| 最新版本入口 | `release/dashboard-version.txt` | `release/agent-version.txt` |
| 源码 | 仓库根目录 Go module | `agent/` 独立 Go module |
| 合仓首版安装包名称 | `dashboard-系统-架构.zip` | `nezha-agent_系统_架构.zip` |

`agent-` 只是区分 Git 标签，不加入程序版本号。两个版本入口都在同一仓库 main 分支；读取后锁定对应不可变标签和资产，不能混用全仓库 Latest 或把两组件版本放在一起比大小。

Agent 继续验证通道清单、来源提交、平台 ZIP 和 SHA-256，拒绝跨组件标签、错误资产、预发行版和普通自动更新降级。哈希与包来自同一个 HTTPS 仓库，用于检测损坏，不等同于独立数字签名。

## 安装与升级

主面板见 [管理说明](../PANEL_MANAGEMENT.md)。现有安装先 `update_script` 再 `update`，备份包含数据库和 `agent-credentials.key` 等加密密钥。

Agent 安装命令由面板生成，同时带 UUID 和该机器独立密钥。脚本地址为本仓库 `agent/scripts/install.sh`（Linux/macOS/FreeBSD）或 `agent/scripts/install.ps1`（Windows）。未使用的认证在「生成认证历史」管理，可跨操作系统复用；不得把另一台机器的认证拿来安装。

v1.0.1 已从统一仓库更新，但不能原地升级为独立目录：v1.0.2 配套主面板 v0.0.4，改用 `DDnezha_系统_架构.zip`、`DDnezha-agent-v1` 通道和 `DDNZ_*` 变量，旧更新器会拒绝新通道。目录迁移需单独执行；迁移完成后的 DDnezha 才按新通道继续自动／强制更新，仍遵守相应禁用开关。详见 [DDnezha 生命周期隔离](ddnezha-isolation.md)。

## 历史合仓迁移（v1.0.0 → v1.0.1）

下列步骤说明此前的仓库合并，不适用于 v1.0.2 的目录／服务隔离。新隔离迁移须按 [独立目录迁移步骤](ddnezha-isolation.md#现有节点迁移) 执行，不能把 DDnezha 覆盖到旧 nezha-agent 路径。

旧 Agent v1.0.0 的更新地址编译在程序里，保留旧仓库不会自动迁移它。需要一次受控程序替换：

1. 按节点确认系统、架构、运行程序、实际配置路径和服务管理方式；备份旧程序、配置及已有安装脚本。
2. 下载并验证统一仓库的正确平台包，检查版本，只替换程序；保持 UUID、独立密钥、面板地址、TLS、禁用开关及多实例服务身份不变。
3. 使用该节点原有服务管理方式恢复连接；核对版本、实时上报、能力声明及配置一致性。失败保留备份并恢复旧程序，不删面板节点或解除封禁。
4. 更新已确认的旧安装脚本副本；二进制升级本身不会更新用户随意保存的所有脚本。特殊路径、Android/OpenWRT、多实例不能直接套用默认安装脚本。
5. 离线节点需等可连接后完成迁移。未确认新版本上报前，不把它标记为已迁移。

升级失败不意味着应该重新生成认证。换机是独立业务，仍须通过「清理数据换机安装命令」按一机一密流程执行。

## 卸载

`cd /opt/DDnezha && ./agent.sh uninstall` 属于独立 POSIX Agent 安装脚本，停止／卸载顶层配置对应服务，成功后才删除其配置；保留程序和备份，不清理面板记录或解除认证封禁。旧脚本可能忽略参数，须先替换，不能用卸载参数试探。

主面板 `./nezha.sh` **没有卸载子命令**。独立 Windows 脚本支持 `.\agent.ps1 uninstall`；两种脚本都只操作有归属标记的独立目录，不接管官方服务。详细行为见 [Agent 说明](../agent/README.md)。

## 维护与发布顺序

- Agent 原提交历史通过非 squash subtree 导入；保留双方原始许可证及署名，Go module 名称不作为下载来源。
- 只递增实际变更组件的版本。不得改写已发布标签／附件；新修复发下一个版本。
- 在准备分支更新版本文件和代码，测试管理脚本、Agent 更新器与安装器，以及主面板和 Agent 的各自 Go module。验证手机／电脑安装入口。
- 面板使用既有已核验的 Linux 构建及 Windows 原生工作流；Agent 使用根目录 `agent-release.yml`，18 个平台构建依赖 Linux／Windows／macOS 测试通过。
- 先创建草稿、上传校验完整的资产，再重新下载核对 SHA-256、ZIP 内容、版本和来源提交。**未经验收不要更新 main 的版本入口。**
- Agent Release 发布时设 `--latest=false`；主面板可保留仓库 Latest，照顾尚未更新脚本的安装。新安装器／更新器都走独立入口，不依赖 Latest。
- 两个组件需要一起发布时，先确认两套资产均已发布并可下载，再把测试提交快进到 main，原子启用两个版本入口。不要把版本文件提前指向尚不存在的安装包。
- 生产部署另行授权；先备份主面板、数据库和密钥，再少量验证、分批迁移节点。回滚不覆盖新产生的业务数据。
