# 正式版本重新编号

本页记录 v0.0.1 / v1.0.0 的重新编号过程，不是要求重复删除旧发行版。当前统一仓库发布为主面板 v0.0.16、Agent v1.0.6，两者继续独立递增。旧 Agent 仓库保留但不再使用；当前更新方式见 [统一仓库说明](unified-repository.md)。

- 主面板：v0.0.1，延续本仓库 custom-* 功能集，不是上游同名旧版。
- 自有 Agent：v1.0.0，包含原自有 v2.3.8 的磁盘读写、双栈上报等能力。
- 源码、Git 标签和提交历史保留。移除 GitHub Release 及其附件不等于删除源码标签。

## 升级次序与身份保护

先备份主面板程序、数据库、配置和加密密钥，完成隔离验收后升级主面板，再验证新 Agent。升级只替换程序，不重新安装或签发认证，不改变任何节点的独立 UUID／密钥、认证封禁、自动检测设置与历史数据。离线或禁止自动更新的节点不会因此立即升级。

新版 Agent 在 Host protobuf 的新增字段 12 中声明 server-transfer-v1 和 mcp-v1。v0.0.1 面板优先使用明确的能力声明；旧 Agent 无声明时保持原版本判断。能力声明不是鉴权凭证，不绕过一机一密、权限或任务开关。旧面板可能根据 1.0.0 的数字误判能力，故必须先升级面板。

## 自动更新与旧发行版

历史自有 Agent 更新器会选择最大的稳定语义版本；因此仅把 v1.0.0 标记为 Latest 不够。备份并验证 v1.0.0 后，按管理员授权移除 v2.3.6、v2.3.7、v2.3.8 三个旧 Release（不删除标签），旧更新器才会选中新版。旧版更新器比较不等而非只允许递增，因此可完成这次正式重新编号。

v1.0.0 的更新器读取旧 Agent 仓库的 Latest；从 v1.0.1 起改读统一仓库独立 Agent 版本入口，并验证 agent-release.json 中的版本、来源提交和 shini74744-agent-v1 通道。普通自动更新不降级；强制更新仍遵守既有禁用强制更新设置。ZIP 必须通过独立 SHA-256 校验，且只包含对应平台的程序；校验、网络或替换失败不回退到上游或其他镜像。

## 发布与回滚边界

面板安装器接受 v0.0.1 和历史 custom-*，资产名与校验流程保持兼容。正式包须分别验证 Linux／Windows 版本输出、运行与源码提交；Agent 的 18 种平台包须验证内容和校验值。

生产回滚以本次备份为准，不恢复到不支持一机一密或双栈记录的更早版本。若回滚到旧面板而节点仍运行新 Agent，服务器迁移／MCP 的版本识别可能受影响。恢复已删除的旧 Agent Release 会改变旧更新器的选版结果，应在明确暂停／控制升级后处理；本地备份不自动重新公开旧包。
